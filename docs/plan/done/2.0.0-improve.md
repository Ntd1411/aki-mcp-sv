## Tóm tắt
Chính thức chốt nâng cấp lên **v2.0.0** (major breaking changes).
Kế hoạch tái cấu trúc toàn diện theo góc nhìn **Non-dev / Packaged**: loại bỏ phụ thuộc môi trường dev (`git`, `npm`, `node` trong runtime app logic) và các package bên thứ ba — **chỉ cho bản đóng gói standalone**, không đụng workflow repo-dev (`npm start` từ git clone), xem mục 3.
Viết lại hoàn toàn các công cụ (đặc biệt là native filesystem tools tinh gọn học hỏi từ DeepSeek harness) gom về một khối in-process, xóa bỏ nút restart hub, giúp app đóng gói siêu gọn và tiến tới mục tiêu **Single Portable Unix Executable File** (hoàn toàn khép kín, zero-dependency).

## 3. Triết lý gói packaged / non-dev & Hướng tới Single Executable File (BREAKING) — CANCELLED (2026-09-03)
Owner reversed packaging: repo is git clone + `npm start`, not a Node-less launcher. Work that would have lived here (HTTP/`!hasGit` update branch, SEA single-binary, `scripts/build/` rewrite) is not happening. Record: `docs/plan/done/remove-package-to-simple-repo.md`. Text below is the pre-cancellation design, kept as the event record of what this item used to ask for.
> chuẩn hóa trọn vẹn triết lý sử dụng: lấy góc nhìn là bản đóng gói tải về từ trang release: dọn mọi lệnh git và lệnh nodejs - những lệnh phụ thuộc môi trường dev. chiến lược này ưu tiên focus vào user sử dụng tiện lợi, non dev. giảm mọi phụ thuộc và sự phức tạp cho users. điều này kéo theo các lệnh check/install update sử dụng http thuần, các native function.

**Scope boundary (làm rõ 2026-08-22, owner yêu cầu)**: "non-dev, zero git/npm/node" chỉ áp dụng cho **bản đóng gói (standalone launcher)**. Real dev chạy trực tiếp từ repo clone (`npm start`) đã có sẵn git/npm/node — vốn là điều kiện để clone được repo — nên **không được đụng tới workflow của họ**. Cách làm: **thêm** nhánh HTTP/native mới cho path standalone, giữ nguyên nhánh git/bash hiện có cho path repo-dev, phân biệt bằng đúng cơ chế `hasGit` (`existsSync(path.join(REPO_ROOT, '.git'))`) đã dùng sẵn cho nút "Pull & restart" trong `panel.js`/`config-page.js` — không phải xóa lệnh git đi.

Liên quan: `docs/plan/done/standalone-release-delivery.md` (đã ship Node-less delivery framework, 1.9.0) — mục này nâng tầm:
- Audit toàn bộ `scripts/` tìm chỗ shell-out `git`/`npm`/`node` bên trong app logic **chỉ trong nhánh chạy khi standalone** (`!hasGit`). Điểm đã xác nhận cần sửa: `panel.js`'s `installRules()` hiện **luôn** git clone/pull + `bash install.sh` bất kể `hasGit` — không có nhánh thay thế cho bản đóng gói (khác với nút self-update app đã phân nhánh đúng). Thay bằng HTTP thuần (đã có sẵn pattern ở `update-check.js` qua `node:https`) + native fs cho nhánh `!hasGit`.
- Tái cấu trúc và tự chủ hoàn toàn mã nguồn các công cụ nội bộ để mở đường đóng gói app thành **một file thực thi duy nhất (single portable unix executable file)** không cần node_modules rời rạc — vẫn chỉ áp dụng cho artifact đóng gói, repo clone vẫn chạy `npm start` bình thường như hiện tại.

**Trạng thái hiện tại so với mục tiêu (2026-08-23)**: `scripts/build/*` hiện đóng gói theo mô hình 3 phần — launcher script (`.command`/`.cmd`/`.run`) tự tải Node runtime rời theo OS/arch từ nodejs.org (`NODE_TARGETS` trong `targets.js`) + giải nén payload app riêng (`APP_ENTRIES`). Đây là "one-click", chưa phải "one file" — Node binary vẫn là asset tải riêng lúc chạy lần đầu. Dependencies hiện tại (`@modelcontextprotocol/sdk`, `zod`, `diff`) đều pure-JS, không có native addon, nên rủi ro kỹ thuật khi chuyển sang single-binary được đánh giá là thấp.

**Ước lượng khối lượng (2026-08-23, chưa xác nhận runtime, chỉ dựa trên đọc code hiện có)**:
- **Phần A — audit & thay thế shell-out (`!hasGit` branch)**: việc đã xác định rõ vị trí (`panel.js`'s `installRules()`), quy mô nhỏ, theo pattern có sẵn (`update-check.js` dùng `node:https`). Không cần nghiên cứu thêm.
- **Phần B — đổi kiến trúc build sang single-binary thật**: chưa có kế hoạch chi tiết, cần:
  1. Prototype Node SEA (Single Executable Applications, built-in Node 20+) cho 1 target trước (`darwin-arm64`) để xác nhận khả thi kỹ thuật.
  2. Viết lại `scripts/build/targets.js`/`launchers.js`/`payload.js`/`package.js` để build ra 1 binary/OS-arch thay vì launcher+Node rời+payload rời.
  3. Sửa `.github/workflows/release.yml` để build & publish asset mới theo pipeline mới.
  4. Verify thật trên cả 4 target (`darwin-arm64`, `darwin-x64`, `linux-x64`, `win32-x64`) — đây là bước chỉ máy thật hoặc CI matrix mới xác nhận được (`coding.B5` rung 5), không thể đóng bằng đọc code tĩnh.
  5. Cập nhật README/docs theo flow build mới.
- **Ballpark thời lượng**: prototype + xác nhận khả thi ~nửa ngày đến 1 ngày làm việc tập trung; phần refactor pipeline + CI matrix + verify đa nền tảng thêm vài ngày làm việc rời rạc — phần lớn thời gian là chờ verify từng OS thật, không phải viết code. Không còn blocker kiến trúc treo (đã gỡ khi mục 7 ship) — thuần là vấn đề ưu tiên thời gian, không phải quyết định còn treo.

## 7. Native Filesystem Tools & Hợp nhất Single Process (Loại bỏ mcp-hub & Restart Hub)
- **Bối cảnh**: Hiện server chạy theo mô hình đa tiến trình với `mcp-hub` điều phối và `@modelcontextprotocol/server-filesystem` chạy qua child process riêng (`npx`). Do package này chỉ nhận thư mục cấp quyền qua CLI args lúc khởi động, nên khi thêm/sửa folder bắt buộc phải có nút *"Apply to file tools (restarts hub)"*, gây gián đoạn kết nối session.
- **Kế hoạch hợp nhất (kế thừa từ `unify-mcp-tools-single-process.md`)**:
  1. **Loại bỏ `mcp-hub` & cổng `19999`**: Đưa toàn bộ việc đăng ký tool về `McpServer` in-process (dùng `StreamableHTTPServerTransport` của SDK hoặc `InMemoryTransport`), bảo toàn cơ chế multiplexing session của claude.ai (tham chiếu `docs/plan/done/bridge-session-churn.md`).
  2. **Native Filesystem Tools**: Tự viết module filesystem native tinh gọn (học hỏi triết lý [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) & Claude Code), tích hợp trực tiếp vào in-process server, đọc quyền truy cập động qua `roots.js:getRoots()` từ `setting.json`.
  3. **Xóa bỏ nút Restart Hub**: Thay đổi thư mục có hiệu lực ngay tại runtime mà không cần khởi động lại hub hay ngắt kết nối client.
  4. **Tối ưu RAM**: Đưa toàn bộ server về **1 tiến trình Node.js duy nhất**, giảm baseline RAM xuống ~40MB.
- **Done**: 4 tiến trình → 1. `filesystem-mcp.js` giữ 7 tool (`read_text_file`, `write_file`, `edit_file`, `create_directory`, `move_file`, `get_file_info`, `list_allowed_directories`), bỏ 7 tool cũ của `@modelcontextprotocol/server-filesystem` (`read_file` alias, `list_directory*`, `directory_tree`, `search_files` — đã có `find_path`/`search_content` thay thế, `read_multiple_files`, `read_media_file` — không dùng thực tế, dễ thêm lại nếu cần). Tên tool giữ nguyên `local__*` (áp qua wrapper trong `tools-server.js`, không đổi tên lần hai).
- **Runtime verification (2026-08-21)**: đo trên `npm start` thật (chi tiết `CHANGELOG.md` [Unreleased]). Session-multiplexing, OAuth DCR round-trip, và folder live-reload không-cần-restart đều pass.
- **RAM root-caused (2026-08-21)**: đo ban đầu ~92MB, không đạt ~40MB. Cô lập từng subsystem bằng `process.memoryUsage()`: Node+zod trần ≈ 40MB (đúng target gốc); import `@modelcontextprotocol/sdk`'s `McpServer` cộng thêm **+27MB cố định** (types.js build toàn bộ zod schema của MCP protocol kể cả resources/prompts/sampling không dùng tới — không có subpath nhẹ hơn trong package.json exports của SDK, không sửa được từ phía repo này). 5 module tool tự viết chỉ cộng ~3MB. ~22MB còn lại do `update-check.js` gọi `fetch()` lúc boot (Node lazy-init `undici`) — đã fix bằng `node:https`, đo lại real run: **~72.6MB**. Kết luận: mục tiêu ~40MB trong bản kế hoạch gốc không tính đến chi phí cố định của SDK chính thức; ~72-76MB mới là sàn thực tế khi còn dùng SDK này, không phải regression cần tiếp tục săn.
